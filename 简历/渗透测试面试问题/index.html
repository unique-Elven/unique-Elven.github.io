一、基础网络与原理（1–8）

1. HTTP 和 HTTPS 的区别

HTTP 是明文传输协议，数据容易被监听或篡改。
HTTPS 在 HTTP 基础上加入 TLS/SSL 加密，通过证书验证服务器身份并对通信内容进行加密，保证数据的机密性和完整性。

2. TLS 握手流程

大致流程：

  1. 客户端发送支持的加密算法

  2. 服务器返回证书和公钥

  3. 客户端验证证书

  4. 客户端生成随机密钥并用公钥加密发送

  5. 双方使用会话密钥进行对称加密通信

3. 什么是三次握手

TCP建立连接需要三次握手：

  1. 客户端发送 SYN

  2. 服务器返回 SYN+ACK

  3. 客户端发送 ACK

这样双方确认发送和接收能力都正常。

一、Web漏洞深挖（1–6）

1. SQL注入为什么会产生？

核心原因：

程序把 用户输入直接拼接到SQL语句中，没有进行参数化处理或过滤。

例如：

SELECT * FROM users WHERE id=’$id’

如果输入：

1 OR 1=1

就会改变SQL逻辑。

本质：
数据和代码没有分离。

防御：

  • 预编译

  • 参数化查询

  • 输入过滤

2. SQL注入为什么有时候没有回显？

原因：

1️⃣ 网站关闭错误信息
2️⃣ 查询结果不返回页面

所以攻击者需要使用：

  • 布尔盲注

  • 时间盲注

通过逻辑判断或延时推断数据。

3. XSS为什么可以读取Cookie？

因为JavaScript可以访问：

document.cookie

如果网站没有设置：

HttpOnly

攻击者就能通过XSS窃取Cookie。

4. 为什么有XSS但拿不到Cookie？

可能原因：

1️⃣ Cookie设置了 HttpOnly
2️⃣ 网站使用 Token认证
3️⃣ CSP安全策略限制

5. 文件上传漏洞为什么会产生？

常见原因：

  • 只检测文件后缀

  • MIME类型检测不严格

  • 文件内容没有检测

攻击者可以上传 WebShell。

6. 什么是反序列化漏洞利用链？

反序列化漏洞通常需要：

gadget chain（利用链）

攻击者构造恶意对象 →
触发类中的特殊方法，例如：

__destruct
__wakeup
__toString

从而执行恶意代码。

一、SQL注入原理（最核心）

原理

SQL注入的本质是：

用户输入被拼接进SQL语句，导致攻击者可以控制SQL逻辑。

示例代码：

$sql = “SELECT * FROM users WHERE username=’$user’ AND password=[已脱敏：password]”;

如果输入：

admin’ OR 1=1 –

SQL变成：

SELECT * FROM users WHERE username=’admin’ OR 1=1 –’ AND password=[已脱敏：password]

OR 1=1 永远成立 → 登录绕过。

利用流程

一般分四步：

1️⃣ 判断是否存在注入
2️⃣ 获取数据库信息

database()
version()

3️⃣ 获取表名

information_schema.tables

4️⃣ 获取字段数据

防御

最核心方法：

  • 预编译（Prepared Statement）

  • 参数化查询

  • ORM

二、XSS漏洞原理

原理

攻击者把恶意JS注入网页，浏览器执行。

例如：

<script>alert(1)</script>

用户访问页面时浏览器执行JS。

XSS分类

1 存储型

攻击代码存数据库
所有用户访问都会触发

例如：

  • 评论区

  • 论坛

2 反射型

攻击代码在URL里

例如：

http://site.com?q=<script>

3 DOM型

JS脚本在浏览器端执行

危害

  • 窃取Cookie

  • 会话劫持

  • 钓鱼页面

防御

核心：

输入过滤
输出编码
Content-Security-Policy

三、SSRF漏洞

面试非常爱问。

原理

服务器端请求用户指定的URL。

例如代码：

file_get_contents($_GET[‘url’])

攻击者输入：

http://127.0.0.1:3306

服务器就会访问内网。

利用场景

SSRF常用于：

  • 扫描内网

  • 攻击Redis

  • 攻击Docker

  • 获取云服务器metadata

例如：

http://169.254.169.254

防御

  • URL白名单

  • 禁止访问内网IP

  • DNS解析校验

四、文件上传漏洞

原理

服务器没有严格检查上传文件类型。

例如：

shell.php

上传后访问：

http://site.com/upload/shell.php

就能执行代码。

常见绕过

1️⃣ 后缀绕过

shell.php.jpg

2️⃣ MIME绕过

3️⃣ 双写绕过

shell.php.php

4️⃣ 大小写绕过

shell.PHP

防御

  • 白名单后缀

  • 随机文件名

  • 上传到非web目录

WAF本质就是：

六、冰蝎流量为什么难检测

很多面试官会问这个。

原理

冰蝎通信流程：

1 客户端生成随机密钥
2 与WebShell通信
3 数据AES加密

所以流量特点：

  • 看不到命令内容

  • 数据是加密的

  • 请求内容随机

如何检测

安全设备一般检测：

1️⃣ 流量特征

固定URL
POST请求
返回长度异常

2️⃣ 行为检测

长连接
频繁通信

3️⃣ 内存检测

检测WebShell加载。

九、Kerberos认证（面试非常爱问）

Kerberos是 域环境认证协议。

核心流程：

1 用户向 KDC 请求票据
2 KDC返回 TGT
3 用户用TGT申请 ST票据
4 用ST访问服务器

关键点：

TGT = Ticket Granting Ticket
ST = Service Ticket

一、 核心 Web 基础与协议

1. PHP 的 Cookie、Session 以及 $_SERVER

  • Cookie 与 Session 的区别：

    • 存储位置： Cookie 存在客户端（浏览器），Session 存在服务端。

    • 安全性： Session 更安全，因为数据在服务器端；Cookie 容易被截获或篡改（这也是为什么安全测试中经常有 Cookie 伪造漏洞）。

    • 联系： Session 默认依赖 Cookie 传递 Session ID（PHPSESSID）。如果浏览器禁用 Cookie，可以通过 URL 重写传参。

  • $_SERVER 变量：

    • 这是一个包含了诸如头信息、路径、脚本位置等信息的超全局数组。常用来获取客户端 IP（$_SERVER['REMOTE_ADDR']）、请求方法（$_SERVER['REQUEST_METHOD']）等。

2. HTTP 协议中的 GET 和 POST 的区别 面试官听腻了“GET 在 URL 里，POST 在 Body 里”这种表面答案，建议用这套话术：

“本质上它们都是 TCP 链接。但在 HTTP 规范和实际应用中：

  1. 语义与幂等性： GET 用于‘获取’资源，是幂等的（多次请求结果一样），可以被浏览器缓存；POST 用于‘提交’数据，非幂等，不会被缓存。

  2. 数据传输位置与限制： GET 的参数拼接在 URL 后，受限于浏览器和服务器对 URL 长度的限制（一般 2KB 左右）；POST 数据在请求体（Body）中，理论上无大小限制。

  3. 安全性： POST 比 GET 相对隐蔽一点，因为参数不在 URL 中明文显示，不会留存在浏览器历史记录中。但在抓包工具面前，如果不套 HTTPS，两者都是明文传输。”

二、 前端基础 (CSS & JavaScript)

你平时写 Vue 项目时，这些底层概念其实都被框架封装好了，面试时需要回归原生：

1. CSS 的 Div 与盒子模型 (Box Model)

  • Div 的概念： div 是一个块级（block-level）元素，它是 HTML 中最常用的容器，用来划分页面结构和布局。

  • 盒子模型（重点）：

    • 所有 HTML 元素都可以看作一个盒子。它由内到外分为四个部分：Content（内容） + Padding（内边距） + Border（边框） + Margin（外边距）。

    • 高阶补充（加分项）： “在实际应用中，我通常会使用 box-sizing: border-box;（IE 盒子模型），这样设置 width 和 height 就直接包含了 padding 和 border，不容易因为调边距导致页面布局撑破。”

2. JavaScript 的使用与 AJAX

  • AJAX (Asynchronous JavaScript and XML)：

    • 核心概念： 允许浏览器与服务器进行异步通信，在不重新加载整个页面的情况下，更新部分网页内容（局部刷新）。

    • 底层原理： 原生主要依赖 XMLHttpRequest 对象（现在更流行用 Fetch API）。通过监听 onreadystatechange 事件来获取服务器返回的数据。

三、 数据库与性能优化

1. 数据库索引与优化 这是一道区分度很高的题，要体现出你的实战经验：

“索引的底层数据结构通常是 B+ 树。它能极大加快 SELECT 查询速度，但会牺牲一定的 INSERT 和 UPDATE 性能，因为每次写操作都要维护索引树。 我的优化思路一般分三步：

  1. 建好索引： 针对经常在 WHERE、ORDER BY、GROUP BY 中出现的字段建立索引。注意避免‘索引失效’的场景（比如对索引列做运算、使用左模糊匹配 LIKE '%abc'）。

  2. SQL 语句优化： 拒绝无脑 SELECT *，只查需要的字段；利用 EXPLAIN 关键字分析查询计划，看是否走到了正确的索引。

  3. 表结构优化： 数据量巨大时考虑分库分表，或者引入 Redis 这种内存型数据库做缓存，减轻 MySQL 的直接读写压力。”
